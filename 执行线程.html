    8. 执行线程

    本章介绍在单个程序中同时执行多段代码：线程（执行线程）以及用于同步它们的工具。大约二十年前，大多数机器只有一个处理器，并行在很大程度上是由操作系统维持的一种假象。如今，即使是最基本的笔记本电脑也有多个核心：多个线程确实在同时运行，这使得这里讨论的同步问题更加普遍。

    Kotlin 在 JVM 上没有自己的线程：它使用 Java 的线程，这些线程自 Java 第一个版本（1996 年）起就通过[Thread] 类、关键字[synchronized]以及[wait] 和[notify] 方法（来自[Object] 类）被集成到 Java 中。Java 5（2004 年）添加了[java.util.concurrent] 包及其子包[java.util.concurrent.locks] 和[java.util.concurrent.atomic]：锁、信号量、并发集合、线程池等。Java 7 添加了[Fork/Join] 框架，Java 8 引入了并行流，Java 21 引入了虚拟线程，所有这些都深刻地改变了服务器的编写方式。Java 25 最终引入了作用域绑定的值（[ScopedValue]）。JDK 框架中的所有这些类都可以在 Kotlin 中直接使用：这是它的主要优势之一。Kotlin 标准库在此基础上增加了一些函数，使它们用起来更方便：[thread] 函数、[withLock] 扩展函数（来自[kotlin.concurrent] 包）、[synchronized] 函数，以及[@Volatile] 和[@Synchronized] 注解……我们将在本章介绍所有这些工具。

    不过，线程并不是 Kotlin 在并发编程方面的最终方案：它原生的异步解决方案是协程，将在第 9 章介绍。它们以线程为基础，而我们在这里要讲的一切（临界区、写入可见性、死锁等）对于完全理解它们仍然至关重要。

    示例位于 Gradle 项目[08-threads]中。每个程序是位于以其命名的包中的一个文件（[threads01/Threads01.kt] 位于包 [threads01] 中……），并通过[gradlew -q run -Pmain=threads01.Threads01Kt]执行，或者在 IntelliJ IDEA 中通过绿色三角形执行。任何程序参数都使用选项[--args]传递给 Gradle：[gradlew -q run -Pmain=threads08.Threads08Kt --args="5"]。

    开始之前先提醒一点：多线程程序的结果每次运行都会有所不同。线程获得处理器访问权的顺序取决于操作系统、处理器数量和机器的负载。本章中重现的结果是在一台与其他高度活跃的程序共享的双处理器 Linux 机器上得到的。如果你运行这些示例，会得到相似的结果，但很少会完全相同。我们会在每种情况下指出哪些结果是可重现的，哪些不是。

    8.1. Thread 类

    应用程序启动时，它运行在一个称为线程的执行流中。对线程建模的类是 JDK 包中的[java.lang.Thread] 类。请回忆一下，Kotlin 把 Java 的访问器[getXxx()] / [setXxx(…)] （以及布尔值的[isXxx()] ）表示为属性：我们写[thread.name = "Main"] 而不是[thread.setName("Main")]。该类的主要构造函数、属性和方法如下：

    如果线程在等待期间被中断，方法[join] 和[sleep] 会抛出异常[InterruptedException]。在 Java 中，这是一个受检异常，编译器要求处理它，或者在[throws] 子句中声明它。Kotlin 没有受检异常（第 3 章）：编译器不会强制要求任何事情。这并不意味着你可以忽略这个异常所表示的含义：我们将在线程中断一节中讨论这一点。

    [Thread] 类还有一个方法[stop]，它曾用于强制终止线程。该方法自 Java 1.2 起就已弃用，自 Java 20 起，它只是抛出[UnsupportedOperationException] 异常：突然停止线程可能会使它正在处理的数据处于不一致的状态。如今，我们是通过中断它，来请求线程协作式地停止：稍后我们会讲到这一点。

package threads01

import java.time.LocalTime
import java.time.format.DateTimeFormatter

fun main() {
    // 执行此代码的线程
    val main = Thread.currentThread()
    // Java 启动器为它指定了名称
    println("Name of the current thread: [${main.name}]")
    // 可以修改
    main.name = "Main"

    // 几个属性
    println("Identifier (threadId): ${main.threadId()}")

    repeat(5) {
        println("${main.name} : ${LocalTime.now().format(format)}")
        // 线程挂起 1 秒
        Thread.sleep(1000)
    }
}

    8.2. 创建执行线程

    可以编写这样的应用程序：其中的代码片段在不同的执行线程中“同时”执行。如果机器的处理器数量少于准备执行的线程数量，这些线程就共享处理器：每个线程轮流在短暂的时间内（几毫秒）获得处理器。在多处理器机器上，多个线程确实在同时执行。分配给线程的时间取决于各种因素，包括它的优先级，该优先级有一个默认值，但可以通过编程方式设置（属性[priority]）；这只是一个指导性的参考，操作系统可以自由地忽略它（Linux 默认就会忽略它）。获得处理器访问权的线程可以提前释放它：

    • 通过等待某个事件（例如用[join]等待另一个线程完成，等待某个信号）；
    • 通过进入睡眠状态一段指定的时间（[sleep]）。

    首先创建线程 T，例如通过构造函数[Thread(task, name)]，其中 [task] 是实现 Java 接口[Runnable]的对象，该接口唯一的方法是[void run()]。借助第 7 章中介绍的SAM 转换，可以传入类型为[() -> Unit] 的 lambda 或函数引用，而不是[Runnable]。在较旧的代码中，我们还会遇到派生自[Thread] 并重新定义其[run] 方法的类：不推荐这样做，因为它把要执行的任务与执行任务的手段混在了一起。

    创建线程并不会启动它：

    • 线程 T 的执行由[T.start()]启动：传给 T 的构造函数的任务的[run] 方法随后将由线程 T 执行。执行[T.start()] 指令的代码不会等待线程 T 结束：它会立即转到下一条指令。现在我们有两个线程在并行运行。它们常常需要相互通信，以跟踪共同工作的进展：这就是线程同步问题；
    • 线程 T 一旦启动，就自主运行。当它正在执行的函数完成时，它就停止；
    • 我们可以使用[T.join()]等待它执行完毕。这是一条阻塞指令：执行它的线程会被阻塞，直到线程 T 完成其工作。这是一种基本的同步方法。

    // 创建执行线程
package threads02

import java.time.LocalTime
import java.time.format.DateTimeFormatter

fun main() {
    // 为主线程命名
    Thread.currentThread().name = "Main"

    // 创建 5 个线程
    val tasks = Array(5) { i ->
        // 第 i 号线程将执行 display 函数；它被命名为 "i"
        Thread(::display, i.toString())
    }
    // 启动它们的执行（非阻塞操作）
    for (task in tasks) {
        task.start()
    }

    // 主线程结束
    println("End of thread ${Thread.currentThread().name} at ${time()}")
}

// 线程所执行的函数：它具有 Runnable.run() 的形状
fun display() {
    // 执行该函数的线程
    val current = Thread.currentThread()
    println("Start of execution of the display function in thread ${current.name}" +
            " (id ${current.threadId()}) : ${time()}")
    // 休眠 1 秒
    sleep(1000)
    println("End of execution of the display function in thread ${current.name} : ${time()}")
}

// 休眠 [ms] 毫秒
fun sleep(ms: Long) {
    try {
        Thread.sleep(ms)
    } catch (_: InterruptedException) {
        // 休眠被中断：恢复线程的中断标志
        Thread.currentThread().interrupt()
    }
}

// 当前时间，精确到毫秒
fun time(): String = LocalTime.now().format(DateTimeFormatter.ofPattern("HH:mm:ss.SSS"))

    注释：

    • 第 9 行：为主线程指定一个名称；
    • 第 12–14 行：创建 5 个线程。函数[Array(5) { i -> … }] 创建一个包含 5 个元素的数组，其中第 i 个元素是 lambda 返回的值。因此线程引用被存储在数组中，以便稍后取用。每个线程执行第 26–33 行中的函数[display] ；
    • 第 14 行：类型为[::display]的函数引用[() -> Unit]被自动转换为[Runnable] 对象：函数[display] 没有参数，也不返回结果，与[run]一样。在 Java 中，在紧凑源文件里，你必须写成[this::display]；在 Kotlin 中，[display] 是一个顶层函数，只需简单地写作[::display]。构造函数的第二个参数是线程名称；
    • 第 17–18 行：启动这些线程。此操作是非阻塞的：线程 #i 与启动它的主线程并行运行；
    • 第 22 行：主线程到达程序末尾；
    • 第 26–33 行：函数[display] 显示执行它的线程的名称和 ID，以及执行的开始和结束时间（精确到毫秒）；
    • 第 32 行：任何执行函数[display] 的线程都会暂停 1 秒钟。处理器随后被交给另一个等待处理器的线程。在 1 秒钟的暂停结束时，暂停的线程重新具备获得处理器的资格。轮到它时，它就会获得处理器；
    • 第 37–42 行：函数[sleep] 封装了[Thread.sleep]。Kotlin 编译器不要求捕获[InterruptedException] 异常，该异常可能由[sleep] 抛出。然而，如果允许它从线程所执行的函数中逃逸，它会使该线程终止，并在控制台上输出一条错误消息。因此函数[sleep] 会捕获它，并重置线程的中断标志（第 42 行）；我们将在中断一节中解释这一操作。赋给子句[_] 的参数的名称[catch] 表示该参数未被使用。我们在本章的大多数程序中都会遇到这个小函数；
    • 第 47 行：函数[time]以表达式（[= …]）的形式编写，按[HH:mm:ss.SSS] 格式返回当前时间（[SSS]：毫秒）。

    • 我们还注意到，显示的顺序并不总是遵循所显示时间的顺序：主线程在 14.490 显示了它的结束，而在此之前已显示了时间为 14.491 和 14.492 的消息。时间是在输出之前计算的，在此期间，另一个线程可能已经向控制台写入了内容。[println] （它调用[System.out.println]）是线程安全的：两个线程写入的两行不会混在一起，但它们的顺序无法保证；

    • 每个线程用[sleep]暂停一秒钟，然后完成函数[display]的执行；

    8.3. 停止线程：中断

    如何在线程完成工作之前停止它，例如当用户取消一个耗时很长的操作时？JVM 不允许你杀死线程；它提供了一种称为中断的协作机制：

    • 每个线程都有一个中断标志，这是一个最初设置为[false]的布尔值；
    • 一个名为 T1 的线程如果想终止线程 T2，就调用[T2.interrupt()]。这会设置 T2 的终止标志。这是一个终止请求：T2 并没有被终止；由该线程自己决定何时以及如何终止自己，以便使其数据保持一致的状态；
    • 如果 T2 阻塞在某个等待方法中（[sleep]、[join]、[wait]，以及[java.util.concurrent] 中的大多数阻塞方法），它就会被唤醒：该方法抛出[InterruptedException] 异常，并且中断标志被重置为[false]；
    • 如果 T2 执行计算而从不等待，它就必须定期使用[Thread.currentThread().isInterrupted] 检查自己的标志。

    在 Java 中，阻塞方法声明了受控异常[InterruptedException]：编译器要求程序员决定如何处理停止请求。Kotlin 不要求这样做，但这个决定仍然需要做出，而且是同一个决定。有两种正确的响应方式：让异常向调用方传播，或者拦截它并干净地结束任务。当这两种方式都不可行时，如程序[sleep] 的函数[Threads02.kt]中那样，就通过[Thread.currentThread().interrupt()] 重置标志，使调用代码仍然能看到该请求。唯一不正确的响应是忽略该异常。程序[Threads05.kt] 演示了这三种情况：

package threads05

import java.time.Duration
import java.time.LocalTime
import java.time.format.DateTimeFormatter

fun main() {
    // 1 - 大部分时间处于休眠的线程
    val sleeper = Thread.ofPlatform().name("sleeper").start {
        var round = 0
        try {
            while (true) {
                round++
                println("${time()} : sleeper, round $round")
                // 如果线程在休眠时被中断，sleep 会抛出 InterruptedException
                Thread.sleep(400)
            }
        } catch (_: InterruptedException) {
            // 中断是一个停止请求：线程干净地完成其工作
            println("${time()} : sleeper interrupted while sleeping, it stops")
        }
    }
    // 2 - 从不休眠、一直在计算的线程
    val calculator = Thread.ofPlatform().name("calculator").start {
        var n = 0L
        // 线程定期检查其中断标志
        while (!Thread.currentThread().isInterrupted) {
            n++
        }
        println("${time()} : calculator interrupted after %,d iterations, it stops".format(n))
    }
    // 3 - 忽略中断的线程（不要效仿）
    val deaf = Thread.ofPlatform().name("deaf").daemon().start {
        repeat(10) {
            try {
                Thread.sleep(400)
            } catch (_: InterruptedException) {
                // 异常被"吞掉"了：停止请求丢失
                println("${time()} : deaf ignores the interruption and continues")
            }
        }
    }

    // 让线程工作 1 秒
    Thread.sleep(1000)
    println("${time()} : Main requests the three threads to stop")
    sleeper.interrupt()
    calculator.interrupt()
    deaf.interrupt()
    // 等待每个线程结束，最多 1 秒
    for (thread in listOf(sleeper, calculator, deaf)) {
        val finished = thread.join(Duration.ofSeconds(1))
        println("${time()} : thread ${thread.name} finished: $finished")
    }
}

    8.4. 虚拟线程

    到目前为止我们创建的线程都是平台线程：每个线程都是对一个操作系统线程的封装，并在其整个生命周期内占用该操作系统线程。操作系统线程是一种昂贵的资源：创建它需要时间，它的栈会预留内存（大约一兆字节），而且系统无法高效地管理超过几千个这样的线程。然而，为每个客户端专门分配一个线程的服务器（见下一段中的图示）大部分时间都在等待：等待数据库的响应、客户端的下一个请求……在这些等待期间，系统线程被阻塞而无法使用。

    Java 21 引入了虚拟线程 （JEP 444），可以在 Kotlin 中原样使用。虚拟线程与任何其他线程一样是一个[Thread] 对象，但它由 Java 虚拟机而不是操作系统管理：

    • 为了执行，虚拟线程被挂载到一个平台线程上，称为它的“载体线程”。载体线程组成一个小型线程池，其大小默认等于处理器的数量；
    • 当虚拟线程阻塞时（[sleep]、等待网络 I/O、锁、阻塞队列等），它会被卸载：它的栈被放到虚拟机的内存中，载体线程立即可用于另一个虚拟线程。当等待结束时，虚拟线程被重新附加到某个宿主线程上——不一定是同一个线程；
    • 一个虚拟线程只占用几百字节：可以创建数百万个。

    Kotlin 协程（第 9 章）基于类似的思想——挂起正在等待的进程而不阻塞系统线程——但它是由 Kotlin 编译器而不是虚拟机实现的。我们将在第 9 章比较这两种方法。

    8.5. 线程的用途

    现在我们已经强调了默认线程的存在——即执行[main] 函数的线程——并且知道了如何创建额外的线程，下面让我们更仔细地看看线程的好处。它们有两个主要用途：

package threads07

import java.time.Duration
import java.time.LocalTime
import java.time.format.DateTimeFormatter
import kotlin.concurrent.thread

// 启动线程与被启动线程之间交换的信息
class Data(
    // 由启动线程设置
    val start: LocalTime,
    val duration: Int,
) {
    // 由被启动线程设置
    lateinit var end: LocalTime
}

fun main() {
    // 为主线程命名
    Thread.currentThread().name = "Main"

    // 创建并启动 5 个线程
    val data = mutableListOf<Data>()
    val tasks = mutableListOf<Thread>()
    for (i in 0..<5) {
        // 与线程交换的对象：启动线程设置开始时间和持续时间
        val d = Data(LocalTime.now(), i + 1)
        data += d
        // 被启动线程通过捕获该对象的 lambda 接收它
        tasks += thread(name = "$i") { sleep(d) }
    }

    // 我们依次等待各个线程
    val format = DateTimeFormatter.ofPattern("HH:mm:ss")
    for ((task, d) in tasks.zip(data)) {
        // 等待线程结束
        task.join()
        // 线程已填写其对象的结束时间
        val actualDuration = Duration.between(d.start, d.end).toMillis() / 1000.0
        println("Thread %s finished: start %s, scheduled duration %d s, end %s, actual duration %.3f s"
            .format(task.name, d.start.format(format), d.duration, d.end.format(format), actualDuration))
    }
    // 主线程结束
    println("End of thread ${Thread.currentThread().name} at ${LocalTime.now().format(format)}")
}

// 线程所执行的函数
fun sleep(data: Data) {
    try {
        // 休眠 [duration] 秒
        Thread.sleep(data.duration * 1000L)
    } catch (_: InterruptedException) {
        Thread.currentThread().interrupt()
    }
    // 被启动线程向启动线程返回一个结果
    data.end = LocalTime.now()
}

    注释：

    • 第 10–16 行：与每个线程交换的信息是一个[Data] 对象。启动线程和被启动线程之间存在双向的信息交换。[start] 和 [duration] 是在主构造函数中声明的[val] 属性：它们在对象构造时一次性设置：
      • [start]：线程的执行开始时间，由启动线程设置；
      • [duration]：被启动线程的睡眠时长（以秒为单位），由启动线程设置；
      • [end]：线程的执行结束时间，由被启动线程设置。这是一个[lateinit var] 属性（第 4 章）：对象构造时它没有值，但它的类型并不是[LocalTime?]。在赋值之前读取它会抛出[UninitializedPropertyAccessException] 异常。对应的 Java 类将近有三十行，包括它的访问器；
    • 第 28–29 行：创建一个 [Data] 对象并将其添加到 [data] 列表中；
    • 第 31 行：lambda[{ sleep(d) }] 捕获变量[d]：被启动的线程将执行第 49–57 行的函数[sleep] ，并以对象[d] 作为参数。运算符[+=] 把函数[thread] 返回的线程添加到可修改的列表[tasks]中；
    • 第 36–42 行：主线程等待它启动的每个线程结束，然后从线程中取出[Data] 对象 并显示其内容。函数[zip] 把这两个列表合并为一个由二元组组成的列表（[Pair<Thread, Data>]），循环[for] 把它解构为[(task, d)]。实际持续时间由[Duration.between(d.start, d.end)]计算；
    • 第 52 行：参数的[duration] 属性设置睡眠时长；
    • 第 57 行：参数的[end] 属性被填充。

    8.7.1. 不同步的并发访问

    在前面一段中，信息只是在两个线程之间、在非常特定的时刻交换的：这是参数传递的一个经典例子。还有其他情况，信息由多个线程共享，这些线程可能希望同时读取或更新它。这就提出了该信息的完整性问题。假设共享的信息是一个包含各种信息 I1、I2、……、In 的结构 S：

    • 线程 T1 开始更新结构 S：它修改了字段 I1，并在完成对结构 S 的完整更新之前被中断；
    • 获得处理器的线程 T2 随后读取结构 S 以做出决策。它读取的是处于不稳定状态的结构：有些字段是最新的，有些则不是。

    这种情况称为对共享资源（这里是结构 S）的并发访问。它往往难以管理。让我们考虑下面的示例，来说明可能出现的问题：

    • 在应用程序结束时，显示计数器的值。因此它应该等于 n。

package threads08

import java.time.LocalTime
import java.time.format.DateTimeFormatter
import kotlin.system.exitProcess

// 共享资源
object Counter {
    // 线程计数器，由所有线程共享；只能在对象内部修改
    var value = 0
        private set

    // 每个线程所执行的函数
    fun increment() {
        val name = Thread.currentThread().name
        // 读取计数器
        val v = value
        println("At ${time()}, thread $name read the counter value: $v")
        // 等待：线程让出处理器
        sleep(1000)
        // 递增计数器
        value = v + 1
        println("At ${time()}, thread $name wrote the counter value: $value")
    }
}

fun main(args: Array<String>) {
    // 检查参数：要创建的线程数
    val nbMaxThreads = 100
    val nbThreads = args.singleOrNull()?.toIntOrNull() ?: -1
    if (nbThreads !in 1..nbMaxThreads) {
        System.err.println("syntax: threads08.Threads08Kt nbThreads (nbThreads between 1 and $nbMaxThreads)")
        exitProcess(1)
    }

    // 创建并启动线程
    val threads = List(nbThreads) { i -> Thread(Counter::increment, "$i") }
    threads.forEach { it.start() }
    // 等待线程结束
    threads.forEach { it.join() }
    // 显示计数器
    println("Number of threads generated: ${Counter.value}")
}

// 休眠 [ms] 毫秒
fun sleep(ms: Long) {
    try {
        Thread.sleep(ms)
    } catch (_: InterruptedException) {
        Thread.currentThread().interrupt()
    }
}

    测试 2 和 3 需要解释一下：它们得出了精确的值。最可能的解释如下：经过一定的执行时间后，虚拟机的即时编译器（JIT）优化了循环[repeat(nbIncrements) { … }] （这是一个[inline]函数，Kotlin 编译器已把它替换为一个简单的循环）：它判定在循环期间不应有其他线程访问计数器（代码中没有任何内容要求这一点），于是把计数器放入处理器寄存器中。随后每个线程读取一次计数器，在其寄存器中给它加上 5000 万，并在最后写回一次。如果各线程的工作没有重叠——这里就是这种情况——结果就是正确的；反之，如果四个线程在任何一个写入之前都读取了值 0，那么四个结果中有三个会丢失——也就是一次丢失 1.5 亿次更新。在这次运行中，只有第一个测试——它在这一优化之前基本已经执行完——丢失了更新；在其他运行中，测试 2 和 3 也可能丢失更新，有时一次丢失 1.5 亿次。这正是这类错误如此危险的原因：程序可以运行数月，然后恰恰在机器负载更重或运行更快的那一天出错。

    问题从何而来？一个线程读取了过时的值，因为另一个线程在完成更新计数器的任务之前被中断了，或者正在另一个处理器上同时工作。这就引出了程序中的临界资源和临界区的概念：

    • 临界资源 是一次只能被一个线程持有的资源。这里的临界资源是计数器；
    • 程序的临界区 是线程执行流中的一段指令序列，线程在其间访问临界资源。我们必须确保，在这个临界区内，该线程是唯一能访问该资源的线程。

    8.7.2. synchronized 函数和 @Synchronized 注解

    在 Java 中，[synchronized] 块按如下方式界定临界区：[synchronized (lock) { …critical section… }]。[lock] 是对所有执行临界区的线程可见的对象。在 JVM 上，每个对象都有一个内部锁，也称为监视器。[synchronized] 块确保一次只有一个线程持有对象 [lock]的监视器，这意味着一次只有一个线程执行临界区：遇到被另一个线程持有的监视器的线程会被阻塞，直到该监视器被释放。无论是正常退出还是因异常退出，监视器都会在退出该块时被释放。

    Kotlin 没有[synchronized] 关键字。取而代之的是，它的标准库提供了一个[synchronized] 函数，其签名为[inline fun <R> synchronized(lock: Any, block: () -> R): R]。得益于尾随 lambda 的语法，对它的调用[synchronized(lock) { …critical section… }] 的写法与 Java 块完全一样。由于该函数是[inline]，Kotlin 编译器会用 lambda 的函数体替换该调用，并用与 JVM 相同的指令把它包围起来，就像 Java 块一样（[monitorenter] / [monitorexit]）：执行上没有任何差别。该函数返回 lambda 的值，这使我们可以写出[val v = synchronized(lock) { counter }]。

    前面的锁在同一个虚拟机内——也就是在同一个进程内——同步线程。有时不同的进程需要共享某个资源，例如文件，或者你可能想防止同一个应用程序的两个实例被启动。JVM 没有提供在进程之间共享的具名同步对象；为此，要使用由操作系统管理的文件锁 ：即[java.nio.channels.FileLock] 类。锁是在已打开的文件上以[FileChannel] 通道的形式获得的：

    • [lock(): FileLock]：等待锁变为可用并获取它；
    • [tryLock(): FileLock?]：尝试不等待地获取锁，如果锁被另一个进程持有，则返回[null] 。Kotlin 把这个 Java 方法的返回值视为平台类型（[FileLock!]）；程序员需要把它当作可能为[null]来处理；
    • [release()]：释放锁。当通道关闭或进程结束时，锁也会被释放，即使进程是被突然终止的：锁不会“成为孤儿”。类[FileLock] 实现了接口[AutoCloseable]：它的方法[close] 调用[release]，因此 Kotlin 函数[use] 可以释放该锁。

import java.nio.channels.FileChannel
import java.nio.file.Path
import java.nio.file.StandardOpenOption.CREATE
import java.nio.file.StandardOpenOption.WRITE
import java.time.LocalTime
import java.time.format.DateTimeFormatter

fun main(args: Array<String>) {

    val file = Path.of(System.getProperty("java.io.tmpdir"), "kotlin-course-threads-12.lock")
    // 进程名称作为参数传入
    val process = args.firstOrNull() ?: "P"

    // 打开文件（如果文件尚不存在则创建）
    FileChannel.open(file, CREATE, WRITE).use { channel ->
        println("${time()} : process $process requests the lock")
        // 不等待的尝试：如果其他进程持有锁则返回 null
        val lock = channel.tryLock() ?: run {
            println("${time()} : the lock is held by another process, $process waits")
            // 无时间限制地等待
            channel.lock()
        }
        // use 在块结束时释放锁（close 会调用 release）
        lock.use {
            // 进程之间的临界区
            println("${time()} : process $process obtained the lock, it works for 3 s")
            Thread.sleep(3000)
            println("${time()} : process $process releases the lock")
        }
    }
}

package threads13

import java.time.LocalTime
import java.time.format.DateTimeFormatter
import java.util.concurrent.Semaphore
import kotlin.system.exitProcess

// 共享资源
object Counter {
    // 线程计数器
    var value = 0
        private set
    // 屏障：一个创建时没有任何许可的信号量，因此处于关闭状态
    val sync = Semaphore(0)

    // 每个线程所执行的函数
    fun increment() {
        val name = Thread.currentThread().name
        println("At ${time()}, thread $name is waiting for permission to enter the critical section")
        // 通过屏障：线程取走唯一的许可，屏障在其身后关闭
        sync.acquireUninterruptibly()
        try {
            // 读取计数器
            val v = value
            println("At ${time()}, thread $name read the counter value: $v")
            // 等待
            sleep(1000)
            // 递增计数器
            value = v + 1
            println("At ${time()}, thread $name wrote the counter value: $value")
        } finally {
            // 许可被归还：屏障为另一个线程打开
            println("At ${time()}, thread $name leaves the critical section")
            sync.release()
        }
    }
}

fun main(args: Array<String>) {
    // 检查参数：要创建的线程数
    val nbMaxThreads = 100
    val nbThreads = args.singleOrNull()?.toIntOrNull() ?: -1
    if (nbThreads !in 1..nbMaxThreads) {
        System.err.println("syntax: threads13.Threads13Kt nbThreads (nbThreads between 1 and $nbMaxThreads)")
        exitProcess(1)
    }

    // 创建并启动线程
    val threads = List(nbThreads) { i -> Thread(Counter::increment, "$i") }
    threads.forEach { it.start() }
    // 让线程到达关闭的屏障
    Thread.sleep(500)
    // 打开临界区的屏障
    Thread.currentThread().name = "Main"
    println("At ${time()}, thread Main opens the barrier of the critical section")
    Counter.sync.release()
    // 等待线程结束
    threads.forEach { it.join() }
    // 显示计数器
    println("Number of threads generated: ${Counter.value}")
}

fun sleep(ms: Long) {
    try {
        Thread.sleep(ms)
    } catch (_: InterruptedException) {
        Thread.currentThread().interrupt()
    }
}

    val threads = List(4) { i ->

                // 等待倒计时到达 0
                start.await()
                println("${time()} : runner $name has started")

                println("${time()} : runner $name gave up")

    start.countDown()
    // 等待线程结束
    threads.forEach { it.join() }
    println("Value of the countdown: ${start.count}")
}

    8.7.7. 写入可见性：@Volatile 注解

    锁不仅仅用于使一组操作不可分割。它们还解决第二个更隐蔽的问题：写入的可见性。为了加快速度，处理器把值存储在它的寄存器和缓存中，而编译器会即时重新排序或消除读写操作，正如我们在程序[Threads09.kt]中所看到的。结果是，一个线程写入的值可能要过一段时间才会被另一个线程看到，或者也许永远看不到。

    Java 内存模型管辖着由 JVM 执行的所有程序——包括 Kotlin 程序——它精确地定义了写入在何时保证可见：当写入与读取之间存在“先行发生”（happens-before）关系时。其中主要的几种如下：

    • 线程在释放锁之前所做的一切（[synchronized] 块的结束、[unlock]）对随后获取该锁的线程都是可见的；
    • 调用线程在[start] 之前所做的一切对被调用线程是可见的；一个线程所做的一切，对通过[join]等待它结束的线程是可见的；
    • 对[volatile] 字段的写入对该字段随后的任何读取都是可见的；
    • [java.util.concurrent] 中的工具提供类似的保证：一个线程在[release()]、[countDown()]、或向并发集合插入元素之前所做的一切，对随后执行[acquire()]、[await()]、或取出该元素的线程是可见的。

    var stop = false
    // 一个 volatile 属性：任何写入对随后的读取都是可见的
    @Volatile
    var volatileStop = false
}

    val t1 = Thread.ofPlatform().name("T1").daemon().start {
        var rounds = 0L
        while (!Flags.stop) {
            rounds++
        }
        println("${time()} : T1 saw the stop request after %,d rounds".format(rounds))
    }
    // 2 - 停止标志是一个 volatile 属性
    val t2 = Thread.ofPlatform().name("T2").daemon().start {
        var rounds = 0L

            rounds++
        }
        println("${time()} : T2 saw the stop request after %,d rounds".format(rounds))
    }

    // 让线程运行一秒钟
    Thread.sleep(1000)
    println("${time()} : Main requests T1 and T2 to stop")

    Flags.volatileStop = true

    for (thread in listOf(t2, t1)) {
        val finished = thread.join(Duration.ofSeconds(2))
        println("${time()} : ${thread.name} finished: $finished")
    }

    8.7.8. 原子类

    [java.util.concurrent.atomic] 包（Java 5）提供了一些类，使对变量的简单操作成为原子的：操作由线程完整地执行，而没有任何其他线程能够在操作中途观察或修改该变量。前面的工具（[synchronized]、[ReentrantLock]、[Semaphore]）都是为了使一组操作成为原子的而设计的，代价是阻塞其他线程。对于简单但频繁的操作，原子类通过使用特殊的处理器指令避免了这种阻塞。[AtomicInteger] 类的主要方法如下：

    方法
    作用
    [get(): Int]、[set(v: Int)]
    读取和写入值（具有[volatile] 字段的语义）
    [incrementAndGet(): Int]、[decrementAndGet(): Int]
    把值递增（递减）1 并返回新值
    [getAndIncrement(): Int]、[getAndDecrement(): Int]
    与上面相同，但返回先前的值（如[x++] 和[x--]）

package threads17

import java.util.concurrent.CountDownLatch
import java.util.concurrent.atomic.AtomicInteger
import java.util.concurrent.atomic.LongAdder
import java.util.concurrent.locks.ReentrantLock
import kotlin.concurrent.withLock

// 共享资源
object Counter {
    // @Volatile 保证写入的可见性，而不保证 value++ 的原子性
    @Volatile
    var value = 0
    private val lock = Any()
    private val reentrantLock = ReentrantLock()
    val atomic = AtomicInteger()
    val adder = LongAdder()

    // 重置计数器
    fun reset() {
        value = 0
        atomic.set(0)
        adder.reset()
    }

    // 读取、递增、写入：非原子操作
    fun withoutSynchronization() {
        value++
    }

    // 由 synchronized 保护的临界区
    fun withSynchronized() {
        synchronized(lock) {
            value++
        }
    }

    // synchronized 函数：锁就是 Counter 对象本身
    @Synchronized
    fun withSynchronizedAnnotation() {
        value++
    }

    // 由 ReentrantLock 保护的临界区
    fun withReentrantLock() {
        reentrantLock.withLock {
            value++
        }
    }

    // 原子递增，无锁
    fun withAtomicInteger() {
        atomic.incrementAndGet()
    }

    // 分布式加法器的递增，无锁
    fun withLongAdder() {
        adder.increment()
    }
}

fun main(args: Array<String>) {
    // 参数：线程数、每个线程的递增次数
    val nbThreads = args.getOrNull(0)?.toInt() ?: 4
    val nbIncrements = args.getOrNull(1)?.toInt() ?: 10_000_000
    println("%d threads, %,d increments per thread, expected value %,d"
        .format(nbThreads, nbIncrements, nbThreads * nbIncrements))

    // 递增共享计数器的六种方式
    val value = { Counter.value.toLong() }
    measure("without synchronization", nbThreads, nbIncrements, Counter::withoutSynchronization, value)
    measure("with synchronized", nbThreads, nbIncrements, Counter::withSynchronized, value)
    measure("with @Synchronized", nbThreads, nbIncrements, Counter::withSynchronizedAnnotation, value)
    measure("with ReentrantLock", nbThreads, nbIncrements, Counter::withReentrantLock, value)
    measure("with AtomicInteger", nbThreads, nbIncrements, Counter::withAtomicInteger) {
        Counter.atomic.get().toLong()
    }
    measure("with LongAdder", nbThreads, nbIncrements, Counter::withLongAdder, Counter.adder::sum)
}

// 启动所有执行 [increment] nbIncrements 次的线程，然后显示 [value]
fun measure(method: String, nbThreads: Int, nbIncrements: Int, increment: () -> Unit, value: () -> Long) {
    Counter.reset()
    // 一个启动信号，使所有线程同时开始
    val startSignal = CountDownLatch(1)
    val threads = List(nbThreads) {
        Thread.ofPlatform().start {
            try {
                startSignal.await()
            } catch (_: InterruptedException) {
                return@start
            }
            repeat(nbIncrements) { increment() }
        }
    }
    // 开始！
    val begin = System.nanoTime()
    startSignal.countDown()
    threads.forEach { it.join() }
    val duration = (System.nanoTime() - begin) / 1_000_000
    println("%-23s : value obtained %,12d in %5d ms".format(method, value(), duration))
}

    8.8. 并发访问多个共享资源

    8.8.1. 死锁

    在前面的示例中，不同线程之间共享的是单个资源。如果有多个资源并且它们相互依赖，情况就会变得更复杂。尤其是可能发生死锁：两个线程相互等待。请看下面依次发生的动作：

    • 线程 T1 获取锁 V1 以访问共享资源 R1；
    • 线程 T2 获取锁 V2 以访问共享资源 R2；
    • 线程 T1 请求锁 V2。它被阻塞；
    • 线程 T2 请求锁 V1。它被阻塞。

    线程 T1 和 T2 无限期地相互等待。有几种可能的解决方案：

    • 使用单个锁同时请求两个资源。如果这会导致长时间锁定一个昂贵的资源，那么这并不总是可行的；
    • 始终按相同的顺序获取锁：如果所有线程都先获取 V1 再获取 V2，就不可能发生死锁。这是最常用的规则；
    • 持有 V1 却无法获取 V2 的线程释放 V1，以避免死锁。

package threads18

import java.time.LocalTime
import java.time.format.DateTimeFormatter
import java.util.concurrent.TimeUnit
import java.util.concurrent.locks.Lock
import java.util.concurrent.locks.ReentrantLock
import kotlin.concurrent.thread
import kotlin.concurrent.withLock
import kotlin.time.Duration
import kotlin.time.Duration.Companion.seconds

fun main() {
    // 两个共享资源的锁
    val lockR1 = ReentrantLock()
    val lockR2 = ReentrantLock()

    // T1 先获取 R1 再请求 R2；2 秒后放弃
    val t1 = thread(name = "T1") { work(lockR1, "R1", lockR2, "R2", 2.seconds) }
    // T2 先获取 R2 再请求 R1；最多等待 5 秒
    val t2 = thread(name = "T2") { work(lockR2, "R2", lockR1, "R1", 5.seconds) }
    t1.join()
    t2.join()
    println("End of Main")
}

// 获取第 1 个资源，然后尝试在 [timeout] 内获取第 2 个
fun work(first: Lock, firstName: String, second: Lock, secondName: String, timeout: Duration) {
    val name = Thread.currentThread().name
    first.withLock {
        println("${time()} : $name obtained $firstName")
        try {
            // 给另一个线程留出获取其第一个资源的时间
            Thread.sleep(500)
            println("${time()} : $name requests $secondName")
            // 带最长等待时间的请求，而不是会无限等待的 lock()
            if (second.tryLock(timeout.inWholeMilliseconds, TimeUnit.MILLISECONDS)) {
                try {
                    println("${time()} : $name obtained $secondName" +
                            " and works with $firstName and $secondName")
                } finally {
                    second.unlock()
                }
            } else {
                println("${time()} : $name did not obtain $secondName in ${timeout.inWholeSeconds} s:" +
                        " it releases $firstName and gives up")
            }
        } catch (_: InterruptedException) {
            Thread.currentThread().interrupt()
        }
    }
}

    • 第 16–17 行：两个资源的锁。这里它们是局部变量，被第 20 行和第 22 行的 lambda 所捕获；

    • 第 22 行：线程 T2 获取 R2，然后请求 R1——也就是按相反的顺序；它最多等待 5 秒钟；
    • 第 29 行：函数[work] 接收由接口[Lock]定义的类型的锁，该接口由[ReentrantLock]实现；
    • 第 31 行：线程使用前面描述的[withLock] 函数获取其第一个资源：无论如何，它都会在块结束时释放它；

    8.8.2. 示例：读者与写者

    请看下面的示例：

    • 我们有一个数组，一些线程向其中写入数据（写者），另一些线程读取数据（读者）；
    • 写者彼此平等但互斥：一次只有一个写者可以向数组中存放数据；
    • 读者彼此平等但互斥：一次只有一个读者可以读取存储在数组中的数据；
    • 只有当写者在数组中放入了数据时，读者才能从数组中读取数据；只有当数组中已有的数据被读者读取之后，写者才能在数组中放入新数据。

    共享资源有两种类型：

    • 可写表：一次只有一个写者可以访问它；
    • 只读表：一次只有一个读者可以访问它。

    以及使用这些资源的顺序：

    • 读者必须始终跟在写者之后；
    • 写者必须始终跟在读者之后，第一次除外。

    对这两个资源的访问可以通过两个[Semaphore] 类型的屏障来控制：

    • [canWrite] 屏障控制写者对数组的访问；
    • [canRead] 屏障控制读者对数组的访问；
    • [canWrite] 屏障被创建为打开状态（一个许可），允许第一个写者通过并阻塞所有其他写者；
    • [canRead] 屏障被创建为关闭状态（没有许可），阻塞所有读者；
    • 当写者完成其工作时，它打开屏障[canRead] ，让一个读者进入；
    • 读线程完成工作后，会打开屏障 [canWrite] ，让一个写线程进入。

    这里可以看到不属于任何线程的屏障的优势：屏障 [canRead] 由读线程关闭（获取许可），由写线程打开（归还许可）。这对锁来说是不可能的，因为锁只能由持有它的线程释放。演示这种同步的程序 [Threads19.kt] 如下：

import java.util.concurrent.Semaphore

import kotlin.random.Random

fun main() {

    // 创建并启动写者线程

    println("End of Main...")
}

// 共享资源及其同步
object Board {
    // 读者和写者之间共享的数组
    private val data = IntArray(3)
    // 表示可以读取 data 的内容：初始为关闭（无许可）
    private val canRead = Semaphore(0)
    // 表示可以写入 data：初始为打开（一个许可）
    private val canWrite = Semaphore(1)

    // 读取数组的内容
    fun read() {
        val name = Thread.currentThread().name
        println("Function [read] started by thread $name")
        // 等待读取许可
        canRead.acquireUninterruptibly()
        // 读取数组
        for (number in data) {
            // 等待 0.5 秒：线程让出处理器
            sleep(500)
            println("${time()} : reader $name read the number $number")
        }
        // 允许一个写者
        canWrite.release()
        println("Function [read] finished by thread $name")
    }

    // 写入数组
    fun write() {
        val name = Thread.currentThread().name
        println("Function [write] started by thread $name")
        // 等待写入许可
        canWrite.acquireUninterruptibly()
        // 写入数组
        for (i in data.indices) {
            // 等待 0.5 秒
            sleep(500)
            // 区间 [0, 1000[ 内的随机数
            data[i] = Random.nextInt(0, 1000)
            println("${time()} : writer $name wrote the number ${data[i]}")
        }
        // 允许一个读者
        canRead.release()
        println("Function [write] finished by thread $name")
    }
}

// 休眠 [ms] 毫秒
fun sleep(ms: Long) {
    try {
        Thread.sleep(ms)
    } catch (_: InterruptedException) {
        Thread.currentThread().interrupt()
    }
}

    8.8.3. wait 和 notifyAll 方法

    在前面的例子中，当写线程在 [canWrite.acquireUninterruptibly()] 语句上阻塞时，其中任意一个线程会被 [canWrite.release()] 操作解除阻塞。如果想为某个特定的写线程打开屏障，事情就会复杂一些。

    以设有服务窗口的公共服务大厅为类比。顾客到达时，从取号机领取一张编号的号牌，然后去坐下。顾客通过扬声器按号码被叫到。等待期间，顾客可以随意做自己的事：看书或打盹。每当扬声器报出一个号码，他们就会被唤醒。如果是自己的号码，顾客就起身前往窗口；否则就继续做原来的事。我们可以用类似的方式处理线程。以写线程为例：

    在 Kotlin 中，这些方法不能直接访问。Kotlin 的根类是 [Any]，而不是 [Object]：编译器会映射这两个类型（*[Any] 会被编译为 *[java.lang.Object]*），但 *[Any] 只声明了三个函数：*[equals]*、[hashCode]、和 [toString]。方法 [wait]、[notify]、和 [notifyAll] （以及 [getClass]）被有意省略：Kotlin 的设计者认为这种底层机制不应充斥所有对象，最好使用 [java.util.concurrent] 提供的工具。如果我们用一个 [val token = Any()] 令牌来编写：

    warning: this class is not recommended for use in Kotlin. Use 'kotlin.Any' instead.

    由于我们的程序是用将警告视为错误的选项编译的（[allWarningsAsErrors = true]），必须通过在使用类 [@Suppress("PLATFORM_CLASS_MAPPED_TO_KOTLIN")] 的声明上添加注解 [Object] 来显式禁用它（[PLATFORM_CLASS_MAPPED_TO_KOTLIN] 是该警告的名称：“与 Kotlin 类关联的平台类”）。我们在下面的令牌声明中一次性完成这件事：它们的类型随后是 [java.lang.Object]，调用 [token.wait()] 和 [token.notifyAll()] 不再触发警告。这个小小的不便是有意为之：在 Kotlin 中，我们更倾向于使用下一节介绍的 [Condition] 接口。尽管如此，熟悉 [wait] 和 [notifyAll] 仍然有用，因为在大量现有的 Java 代码中都会遇到它们。

    下面我们描述一种标准模式——Brian Goetz 等人的著作 [Java Concurrency in Practice] 中尤其介绍过——它可以解决带有进入条件的屏障问题。

    共享资源（计数器）的线程通过一个我们称为 令牌的对象来访问它：它是一个简单对象（[Object()]），使用的是它的监视器。要通过通向计数器的屏障，必须持有令牌，而令牌只有一个。因此线程之间必须相互传递令牌。

    要前往计数器，线程首先使用 [synchronized(token) { … }] 块请求令牌。如果获得令牌，它就在 [while (!iAmTheExpectedOne) { token.wait() }] 循环中检查自己是否满足前往计数器的条件，然后仍在 [synchronized] 块内前往计数器。如果该线程不是计数器处所期待的线程，它就通过 [token.wait()] 归还令牌，让出自己的轮次，并进入阻塞状态。当另一个线程发出访问条件发生变化的信号时，它会被唤醒；然后它会取回令牌并再次检查条件。这就是为什么此处的测试是循环（[while]) 而不是简单的 [if]。还有第二个原因，是 JVM 特有的：规范允许“虚假唤醒”，即 [wait] 在没有任何线程调用 [notify] 的情况下结束；循环使这种情况无害。[token.wait()] 操作只能由持有令牌监视器的线程执行；否则会抛出 [IllegalMonitorStateException] 异常。在这种方案中，令牌只有在事务完成之后才会释放。

    修改计数器访问条件的线程同样必须持有令牌，并通知等待中的线程：它在 [synchronized(token) { … }] 块内修改计数器的访问条件，然后使用 [token.notifyAll()] 唤醒等待中的线程。

    唤醒线程意味着等待中的线程成为令牌的候选者；它们并不会立即获得令牌。只有在 [synchronized] 块结束时令牌才可用。所有被唤醒的线程随后会 依次以不确定的顺序获得令牌，从而有机会再次检查访问条件。第一个满足条件的线程保留令牌并前往窗口排队。

import java.time.LocalTime
import java.time.format.DateTimeFormatter

import kotlin.random.Random

    val nbThreads = 3

    // 读者的顺序：与创建顺序相反
    Board.readOrder = List(nbThreads) { i -> "R${nbThreads - 1 - i}" }
    // 写者的顺序：创建顺序

        synchronized(canWrite) {
            writingAllowed = true
            // 唤醒所有等待该令牌的写者
            canWrite.notifyAll()
        }
    }

    fun read() {

        println("Function [read] started by thread $name")

            try {
                // 只要还没轮到我们，就归还令牌并等待
                while (!readingAllowed || readOrder[nextReader] != name) {
                    canRead.wait()
                }
            } catch (_: InterruptedException) {
                return
            }

            for (number in data) {
                sleep(500)
                println("${time()} : reader $name read the number $number")
            }
            // 下一个读者
            readingAllowed = false
            nextReader++
            // 通知写者可以写入了
            synchronized(canWrite) {
                writingAllowed = true
                canWrite.notifyAll()
            }
            println("Function [read] finished by thread $name")
        }
    }

    // 写入数组
    fun write() {
        val name = Thread.currentThread().name
        println("Function [write] started by thread $name")
        // 请求写计数器的令牌
        synchronized(canWrite) {
            try {
                // 只要还没轮到我们，就归还令牌并等待
                while (!writingAllowed || writeOrder[nextWriter] != name) {
                    canWrite.wait()
                }
            } catch (_: InterruptedException) {
                return
            }
            // 在计数器处：写入数组
            for (i in data.indices) {
                sleep(500)
                data[i] = Random.nextInt(0, 1000)
                println("${time()} : writer $name wrote the number ${data[i]}")
            }
            // 下一个写者
            writingAllowed = false
            nextWriter++
            // 通知读者可以读取了
            synchronized(canRead) {
                readingAllowed = true
                canRead.notifyAll()
            }
            println("Function [write] finished by thread $name")
        }
    }
}

    8.8.4. 条件：Condition 接口

    方法 [wait] 和 [notifyAll] 与对象的监视器相关联，因此与 [synchronized] 块相关联。对于锁 [ReentrantLock]，对应的是接口 [java.util.concurrent.locks.Condition]：[Condition] 对象由锁的 [newCondition()] 方法创建，并提供方法 [await()] （相当于 [wait]）、[await(time: Long, unit: TimeUnit)]、[signal()] （相当于 [notify]）以及 [signalAll()] （相当于 [notifyAll]）。它们的用法遵循相同的规则：线程必须持有锁，并且访问条件要在 [while] 循环中测试。这些都是 Java 接口的标准方法：Kotlin 调用它们时无需类型转换，也没有警告。这是 Kotlin 中的首选方案。

    8.8.5. 多个读线程同时读取：ReadWriteLock

    在前面的例子中，读线程是互斥的。在许多应用中，这种限制没有必要：当没有人修改数据时，多个线程可以同时读取。只有写入必须是互斥的：当某个写线程正在修改数据时，任何读线程或其他写线程都不应能访问它。这就是经典的 读写问题，由 [java.util.concurrent.locks.ReadWriteLock] 接口解决。[ReadWriteLock] 对象提供两个相互关联的锁：

    • [readLock()]：读锁，只要没有线程持有写锁，就可以被多个线程同时持有；
    • [writeLock()]：写锁，是互斥的。

class Catalog {
    private val prices = mutableMapOf("keyboard" to 20, "mouse" to 10)
    // 读者一把锁，写者一把锁
    private val lock = ReentrantReadWriteLock()

    // 多个线程可以同时持有读锁
    fun readPrice(article: String): Int = lock.read {
        val name = Thread.currentThread().name
        println("${time()} : $name starts reading the price of $article")
        // 长时间读取
        sleep(1000)
        val p = prices.getValue(article)
        println("${time()} : $name read the price of $article: $p")
        p
    }

    // 写锁是独占的：没有读者，也没有其他写者
    fun changePrice(article: String, newPrice: Int) {
        val name = Thread.currentThread().name
        println("${time()} : $name requests the write lock")
        lock.write {
            println("${time()} : $name starts changing the price of $article")
            // 长时间写入
            sleep(1000)
            prices[article] = newPrice
            println("${time()} : $name set the price of $article to $newPrice")
        }
    }
}

    • 第二批读线程在写线程到达之后才开始，它们等待修改完成，然后读取新的价格。因此锁 [ReentrantReadWriteLock] 可以防止源源不断的读线程无限期地阻止写线程写入：在写线程等待期间到达的读线程排在写线程之后。这个顺序是可重现的；只有每一批内部读线程的顺序会变化。

    只有在读取次数很多且足够耗时的情况下，读写锁才有用。对于非常短的读取，[StampedLock] 类（Java 8）提供“乐观”读取——不加锁——并在事后进行验证。而对于读取非常频繁、修改很少的集合，下一段介绍的并发集合通常是最佳方案。

    8.9. 并发集合

    前面的例子保护的是非常简单的共享数据（一个计数器、一个数组、一个小字典）。当线程共享一个集合（列表、字典、队列）时，可以用锁保护每一次访问。但是普通的可变集合——无论是 Kotlin 中的（[mutableListOf]、[mutableMapOf]、[ArrayDeque]）还是 Java 中的（[ArrayList]、[HashMap]）——并不是为被多个线程同时修改而设计的：不加保护地使用可能导致元素丢失，触发意外的异常（[ConcurrentModificationException]），甚至破坏集合的内部结构。Kotlin 的“只读”集合（[List]、[Map]）也是如此：这种类型只是阻止接收它的代码修改集合，并不保证其他人不会修改它。方法 [Collections.synchronizedList(…)]、[Collections.synchronizedMap(…)]… 把普通集合包装成一个每个方法都是 [synchronized] 类型的对象：这样做是安全的，但所有线程都争用同一把锁，而且对集合的迭代仍需手动保护。自 Java 5 起，[java.util.concurrent] 包就提供了无需显式加锁即可在线程之间共享的集合。Kotlin 标准库在 JVM 上没有对应的实现：我们直接使用 JDK 中的集合，它们实现了 [MutableList] 和 [MutableMap] 接口……因此可以像 Kotlin 集合一样使用（[+=]、[[ ]]、[for]、[filter]、[map]…）：

package threads23

import java.util.concurrent.ConcurrentHashMap
import java.util.concurrent.CopyOnWriteArrayList
import kotlin.concurrent.thread
import kotlin.random.Random

fun main() {
    // 共享字典：数字 -> 抽取次数
    val draws = ConcurrentHashMap<Int, Int>()
    // 各线程报告的共享列表
    val reports = CopyOnWriteArrayList<String>()

    // 4 个线程各自随机抽取 100,000 个数字
    val nbDraws = 100_000
    val threads = List(4) { i ->
        thread(name = "T$i") {
            repeat(nbDraws) {
                val digit = Random.nextInt(0, 10)
                // 添加值为 1 的键，或原子地更新已有的值
                draws.merge(digit, 1, Int::plus)
            }
            // 报告已添加到列表
            val name = Thread.currentThread().name
            reports += "thread %s finished its %,d draws".format(name, nbDraws)
        }
    }
    threads.forEach { it.join() }

    // 报告，按到达顺序排列
    for (report in reports) {
        println(report)
    }
    // 抽取结果，按键的顺序排列
    for ((digit, count) in draws.toSortedMap()) {
        println("digit %d : %,6d draws".format(digit, count))
    }
    val total = draws.values.sum()
    println("total: %,d draws (expected: %,d)".format(total, threads.size * nbDraws))

    8.9.2. 生产者与消费者：BlockingQueue

    读写问题是经典的 生产者-消费者问题的一个变体：一些线程生产数据，另一些线程消费数据。[BlockingQueue<E>] 接口无需任何显式的同步工具就能解决这个问题：

    • [put(element)] 将一个元素入队。如果队列容量有限且已满，生产者将被阻塞，直到有空位；
    • [take()] 移除队首的元素。如果队列为空，消费者将被阻塞，直到有元素到达；
    • [offer(element, timeout, unit)] 和 [poll(timeout, unit)] 做同样的事，但有最长等待时间；[offer(element)] 和 [poll()]没有超时，从不阻塞：失败时它们返回 [false] 或 [null] （在 Kotlin 中，[poll] 返回平台类型 [Int!]，应将其视为 [Int?]）。

package threads24

import java.time.LocalTime
import java.time.format.DateTimeFormatter
import java.util.concurrent.ArrayBlockingQueue
import java.util.concurrent.BlockingQueue
import kotlin.concurrent.thread

// 表示生产结束的值（"毒丸"）
const val END = -1

fun main() {
    // 一个最多容纳 3 个元素的队列
    val queue: BlockingQueue<Int> = ArrayBlockingQueue(3)
    val nbConsumers = 2

    // 生产者放入 8 个数字，然后发出已完成的信号
    val producer = thread(start = false, name = "P") {
        try {
            for (i in 1..8) {
                // 如果队列已满则阻塞
                queue.put(i)
                println("${time()} : P put $i (waiting elements: ${queue.size})")
                Thread.sleep(100)
            }
            // 每个消费者一个结束标记
            repeat(nbConsumers) { queue.put(END) }
            println("${time()} : P has finished")
        } catch (_: InterruptedException) {
            Thread.currentThread().interrupt()
        }
    }

    // 两个消费者取数字，直到遇到结束标记
    val consumers = List(nbConsumers) { i ->
        thread(start = false, name = "C${i + 1}") {
            val name = Thread.currentThread().name
            try {
                while (true) {
                    // 如果队列为空则阻塞
                    val number = queue.take()
                    if (number == END) break
                    println("${time()} : $name took $number")
                    // 处理该数字
                    Thread.sleep(600)
                }
                println("${time()} : $name has finished")
            } catch (_: InterruptedException) {
                Thread.currentThread().interrupt()
            }
        }
    }

    // 启动并等待所有线程
    val all = listOf(producer) + consumers
    all.forEach { it.start() }
    all.forEach { it.join() }
}

// 当前时间，精确到毫秒
fun time(): String = LocalTime.now().format(DateTimeFormatter.ofPattern("HH:mm:ss.SSS"))

    8.10. 线程池：ExecutorService

    8.10.1. 原理

    到目前为止，为了管理线程，我们都是先创建线程再启动它，或者通过 [start()] ，或者通过 [thread] 函数。创建平台线程是一项相对昂贵的操作：尤其是系统必须为它分配栈，而且每个线程在存在期间都会占用内存。我们将在第 10 章看到连接池的存在：已打开的连接被保留备用，并借给请求它们的线程，因为打开连接的开销很大。线程也有类似的机制：线程池。

    JDK 类通过 [java.util.concurrent.ExecutorService] 接口（“执行器”）来表示线程池：不再创建线程，而是把 任务分配给执行器，由它的线程来执行。完成了任务的线程不会被销毁，而是接着处理下一个任务。[ThreadPoolExecutor] 类是最常见的实现，其工作方式如下：

    • 它有 固定数量的线程（“核心线程池大小”）：只要未达到这个数量，每个新任务都会触发创建一个新线程；
    • 超过这个数量后，任务被放入一个 队列 （一个 [BlockingQueue]），线程从中取出任务；
    • 如果队列已满，线程池会创建额外的线程，直到达到 最大数量（“最大线程池大小”）。这些额外的线程如果空闲超过一定时间就会被销毁；
    • 如果已达到最大数量且队列已满，任务就会被 拒绝：默认情况下，提交该任务的方法会抛出 [RejectedExecutionException] 异常。

    线程池有两个优点：它节省了创建线程所花的时间（少量线程就能处理数百个请求），并且通过限制线程数量，防止应用程序被过多的请求压垮。

    执行器通过其方法 [shutdown] 终止（它不再接受新任务，已提交的任务完成后其线程停止），之后还可以接着调用 [awaitTermination] （等待任务完成），或者调用 [shutdownNow] （中断正在执行的任务）。从 Java 19 起，[ExecutorService] 扩展了 [AutoCloseable] 接口：它的 [close] 方法调用 [shutdown] ，然后等待所有任务完成。因此在 Kotlin 中，可以在 [use { … }] 块内使用执行器——这是 [AutoCloseable] 的扩展函数，用来取代 Java 的带资源的 [try] 语句（第 3 章）——退出该块时，所有已分配的任务都已完成。程序 [Threads25.kt] 如下：

package threads25

import java.time.Duration
import java.time.LocalTime
import java.time.format.DateTimeFormatter
import java.util.concurrent.ArrayBlockingQueue
import java.util.concurrent.RejectedExecutionException
import java.util.concurrent.ThreadPoolExecutor
import java.util.concurrent.TimeUnit

// 传递给每个作业的信息
data class Data(val number: Int, val start: LocalTime, val duration: Int)

fun main() {
    Thread.currentThread().name = "Main"
    // 3 个常驻线程，最多 5 个线程，一个容纳 2 个作业的等待队列
    ThreadPoolExecutor(3, 5, 60, TimeUnit.SECONDS, ArrayBlockingQueue(2)).use { pool ->
        // 8 个各 3 秒的作业交给线程池
        for (i in 0..<8) {
            val data = Data(i, LocalTime.now(), 3)
            try {
                pool.execute { sleep(data, pool) }
            } catch (_: RejectedExecutionException) {
                println("${time()} : job no. $i was rejected by the pool")
            }
        }
        println("${time()} : thread Main handed the jobs to the pool and waits for their end")
        // use 块结束时关闭线程池：close() 等待已提交的作业结束
    }
    println("${time()} : end of thread Main")
}

// 由线程池中的线程执行的作业
fun sleep(data: Data, pool: ThreadPoolExecutor) {
    // 线程池的状态
    val name = Thread.currentThread().name
    println("${time()} : job no. ${data.number} starts in thread $name" +
            " (threads: ${pool.poolSize}, active: ${pool.activeCount}, queued: ${pool.queue.size})")
    // 休眠 [duration] 秒
    try {
        Thread.sleep(data.duration * 1000L)
    } catch (_: InterruptedException) {
        Thread.currentThread().interrupt()
    }
    val duration = Duration.between(data.start, LocalTime.now()).toMillis() / 1000.0
    println("%s : job no. %d ends: scheduled for %d s, it lasted %.2f s since it was requested"
            .format(time(), data.number, data.duration, duration))
}

package threads26

import java.time.LocalTime
import java.time.format.DateTimeFormatter
import java.util.concurrent.Callable
import java.util.concurrent.ExecutionException
import java.util.concurrent.Executors
import java.util.concurrent.Future

fun main() {
    println("Main thread: ${Thread.currentThread()}")

    // 1 - 一个 2 个线程的线程池，在 use 块结束时自动关闭
    Executors.newFixedThreadPool(2).use { pool ->
        // 三个任务，各自返回一个 Int 类型的结果
        val futures: List<Future<Int>> = List(3) { number ->
            pool.submit<Int> {
                val name = Thread.currentThread().name
                println("${time()} : task $number runs in thread $name")
                // 工作
                Thread.sleep(500L * (number + 1))
                // 任务的结果
                number * 10
            }
        }
        // 结果：get() 等待任务结束
        futures.forEachIndexed { i, future ->
            try {
                println("task $i: result ${future.get()}, state ${future.state()}")
            } catch (e: ExecutionException) {
                println("task $i in error: ${e.cause}")
            }
        }

        // 一个抛出异常的任务
        val failed = pool.submit<Int> { fail() }
        try {
            failed.get()
        } catch (e: ExecutionException) {
            // 任务的异常被包装在 ExecutionException 中
            val cause = e.cause!!
            println("${e::class.simpleName} containing ${cause::class.simpleName} : ${cause.message}")
        }
        println("task in error: state ${failed.state()}")
    }

    // 2 - 每个任务一个虚拟线程；invokeAll 提交一组任务并等待它们结束
    Executors.newVirtualThreadPerTaskExecutor().use { executor ->
        val jobs = List(3) { number ->
            Callable {
                Thread.sleep(300)
                "job $number executed by ${Thread.currentThread()}"
            }
        }
        for (future in executor.invokeAll(jobs)) {
            // 任务已完成：resultNow() 无需等待即可返回其结果
            println(future.resultNow())
        }
    }
}

package threads27

import java.time.LocalTime
import java.time.format.DateTimeFormatter
import java.util.concurrent.ConcurrentHashMap
import java.util.concurrent.ForkJoinPool
import java.util.stream.IntStream
import kotlin.time.measureTimedValue

fun main() {
    // 1 - 统计小于 N 的素数个数
    val N = 5_000_000
    // 顺序版本：for 循环
    val (nbLoop, durationLoop) = measureTimedValue {
        var nb = 0
        for (i in 2..<N) {
            if (isPrime(i)) nb++
        }
        nb
    }
    display("sequential for", nbLoop.toLong(), durationLoop.inWholeMilliseconds)

    // 顺序版本：Kotlin 对区间的 count 函数
    val (nbKotlin, durationKotlin) = measureTimedValue { (2..<N).count { isPrime(it) } }
    display("sequential count", nbKotlin.toLong(), durationKotlin.inWholeMilliseconds)

    // 顺序版本：Java 流
    val (nbStream, durationStream) = measureTimedValue { IntStream.range(2, N).filter { isPrime(it) }.count() }
    display("sequential stream", nbStream, durationStream.inWholeMilliseconds)

    // 并行版本：同一个流，改为并行
    val (nbParallel, durationParallel) = measureTimedValue {
        IntStream.range(2, N).parallel().filter { isPrime(it) }.count()
    }
    display("parallel stream", nbParallel, durationParallel.inWholeMilliseconds)

    // 参与工作的线程以及每个线程找到的素数个数
    val threads = ConcurrentHashMap<String, Int>()
    IntStream.range(2, N).parallel()
        .filter { isPrime(it) }
        .forEach { threads.merge(Thread.currentThread().name, 1, Int::plus) }
    for ((name, nb) in threads.toSortedMap()) {
        println("  thread %-30s : %,d prime numbers found".format(name, nb))
    }

    // 2 - 并行处理一个集合
    val files = listOf("a.txt", "b.txt", "c.txt", "d.txt", "e.txt")
    files.parallelStream().forEach { file ->
        println("${time()} : processing of $file in thread ${Thread.currentThread().name}")
        // 模拟处理
        sleep(500)
    }
    println("parallel forEach finished")
    println("Parallelism of the common pool: ${ForkJoinPool.getCommonPoolParallelism()}")
}

// 素性测试（刻意写得很简单）
fun isPrime(n: Int): Boolean {
    if (n < 2) return false
    var d = 2
    while (d * d <= n) {
        if (n % d == 0) return false
        d++
    }
    return true
}

import java.util.concurrent.ConcurrentHashMap
import java.util.concurrent.ForkJoinPool
import java.util.concurrent.RecursiveTask
import kotlin.time.measureTimedValue

fun main() {
    val N = 5_000_000
    // 公共池，并行流默认使用
    val (nb, duration) = measureTimedValue { ForkJoinPool.commonPool().invoke(CountPrimes(2, N)) }
    println("common pool       : %,d prime numbers in %d ms".format(nb, duration.inWholeMilliseconds))

    // 一个 4 个线程的线程池，在 use 块结束时关闭
    ForkJoinPool(4).use { pool ->
        CountPrimes.chunks.clear()
        val (nb4, duration4) = measureTimedValue { pool.invoke(CountPrimes(2, N)) }
        println("pool of 4 threads : %,d prime numbers in %d ms".format(nb4, duration4.inWholeMilliseconds))
        println("tasks stolen by one thread from another: ${pool.stealCount}")
    }
    // 各数据块在上一个线程池的线程间的分布
    for ((name, nbChunks) in CountPrimes.chunks.toSortedMap()) {
        println("  %-25s : %d chunks processed".format(name, nbChunks))
    }
}

// 一个统计区间 [start, end[ 内素数个数的任务
class CountPrimes(private val start: Int, private val end: Int) : RecursiveTask<Int>() {
    companion object {
        // 低于此阈值时，直接处理该数据块
        const val THRESHOLD = 100_000
        // 每个线程处理的数据块数量
        val chunks = ConcurrentHashMap<String, Int>()
    }

    override fun compute(): Int {
        // 数据块足够小：按顺序处理
        if (end - start <= THRESHOLD) {
            chunks.merge(Thread.currentThread().name, 1, Int::plus)
            return (start..<end).count { isPrime(it) }
        }
        // 否则，将其一分为二
        val middle = (start + end) ushr 1
        val left = CountPrimes(start, middle)
        val right = CountPrimes(middle, end)
        // 左半部分交给线程池（另一个线程可能会"窃取"它）
        left.fork()
        // 右半部分由当前线程处理
        val nbRight = right.compute()
        // 我们等待左半部分的结果，并合并两个结果
        return left.join() + nbRight
    }
}

// 素性测试（刻意写得很简单）
fun isPrime(n: Int): Boolean {
    if (n < 2) return false
    var d = 2
    while (d * d <= n) {
        if (n % d == 0) return false
        d++
    }
    return true
}

    8.12. 线程局部数据

    8.12.1. 原理

    考虑一个三层应用程序：

    假设该应用程序是多用户的，例如 Web 应用程序。每个用户请求由一个线程处理。线程的生命周期如下：

    • 创建线程（虚拟线程）或从线程池中请求一个线程来满足用户的请求；
    • 如果该请求需要数据，线程会执行 [ui] 层的一个函数，该函数调用 [business] 层的一个函数，后者又调用 [dao] 层的一个函数；
    • 线程向用户返回响应。随后它要么终止，要么被归还给线程池。

    在第二步中，让线程拥有自己的数据——即不与其他线程共享的数据——可能会很有用。例如，这些数据可以属于该线程所服务的特定用户，并在各个 [ui, business, dao] 层中使用，而不必作为参数传递给每个函数。

    JDK 为此提供了两种工具，Kotlin 原样使用它们：

    • [ThreadLocal<T>] 类（Java 1.2）：这是一个对象，其值——通过 [get()] 读取，通过 [set(value)] 写入——对每个线程都不同。构造函数 [ThreadLocal.withInitial(factory)] 为每个线程提供初始值；方法 [remove()] 清除当前线程的值。派生类 [InheritableThreadLocal<T>] 把创建线程的值传递给新创建的线程；
    • [ScopedValue<T>] 类（在 Java 25 中为正式特性）：一个在有限的代码范围内绑定到线程的值，在该范围内不能被修改。

object Context {

    @Volatile
    var shared = 0

fun main() {

    // 主线程写入自己的值
    Context.shared = 100
    Context.perThread.set(100)
    Context.user.set("admin")
    Context.language.set("fr")

    // 三个线程写入后再次读取数据
    val threads = List(3) { number ->

            // 写入
            Context.shared = number
            Context.perThread.set(number)

            // 再次读取
            display()
        }
    }
    threads.forEach { it.join() }
    // 主线程再次读取
    display()
}

    8.12.3. ScopedValue 类

    [ScopedValue<T>] 值在一段代码的执行期间被 绑定 到某个值，这段代码称为它的 作用域：

    • [ScopedValue.newInstance()] 创建一个绑定值，通常存放在顶层属性或对象的属性中，该属性是只读的（[val]）；
    • [ScopedValue.where(sv, value).run(action)] 执行该操作（一个 [Runnable]），并将 [sv] 绑定到 [value]。当该操作——以及它调用的所有函数——在当前线程中执行时，[sv.get()] 返回 [value]。操作结束后，绑定随之消失：无需清理；
    • [ScopedValue.where(sv, value).call(op)] 对返回结果的操作做同样的事；
    • 在作用域内，该值不能被修改；它只能在嵌套作用域中被绑定到另一个值；
    • [isBound()] 指示该值是否在当前线程中已绑定（Kotlin 将其视为属性 [isBound]）；[orElse(other)] 返回绑定的值，如果未绑定，则返回 [other]。在任何作用域之外，[get()] 会抛出 [NoSuchElementException] 异常。

class Transaction {
    companion object {
        private val counter = AtomicInteger()
    }

    private val undos = ArrayDeque<() -> Unit>()
    val number = counter.incrementAndGet()

    // 记录撤销某次更新的操作
    fun log(undo: () -> Unit) {
        undos.addFirst(undo)
    }

    // 提交事务：保留更新
    fun commit() {
        undos.clear()
    }

    // 回滚事务：撤销更新，从最后一个到第一个
    fun rollback() {
        while (true) {
            val undo = undos.removeFirstOrNull() ?: break
            undo()
        }
    }
}

    private val lock = Any()
    private var nextId = 1

    override fun insertArticle(article: Article): Int {
        // 当前线程中是否有正在进行的事务？
        val transaction = ThreadContext.transaction.get()
        synchronized(lock) {
            check(table.none { it.name == article.name }) { "an article named [${article.name}] already exists" }
            val inserted = article.copy(id = nextId++)
            table += inserted
            // 在事务中，我们记录如何撤销插入
            transaction?.log {
                synchronized(lock) { table -= inserted }
            }
            val mode = if (transaction == null) "outside a transaction"
                       else "in transaction ${transaction.number}"
            val name = Thread.currentThread().name
            println("[$name] [dao] insertion of ${inserted.name} (id ${inserted.id}) $mode")
            return 1
        }
    }

    override fun getAllArticles(): List<Article> = synchronized(lock) { table.toList() }

    override fun deleteAllArticles() {
        synchronized(lock) { table.clear() }
    }

class Business(private val dao: IDao) : IBusiness {
    // 插入一个商品列表：要么全部成功，要么全部失败
    override fun insertArticlesInTransaction(articles: List<Article>) {
        val name = Thread.currentThread().name
        // 事务开始，存储在线程局部数据中
        val transaction = Transaction()
        ThreadContext.transaction.set(transaction)
        try {
            for (article in articles) {
                // [dao] 层将在线程中找到该事务
                dao.insertArticle(article)
                // 模拟处理，给其他线程介入的时间
                sleep(200)
            }
            transaction.commit()
            println("[$name] [business] transaction ${transaction.number} committed")
        } catch (e: RuntimeException) {
            transaction.rollback()
            println("[$name] [business] transaction ${transaction.number} rolled back")
            // 异常被重新抛给调用者
            throw e
        } finally {
            // 线程不再有正在进行的事务
            ThreadContext.transaction.remove()
        }
    }

    // 不使用事务插入一个商品列表
    override fun insertArticlesOutOfTransaction(articles: List<Article>) {
        articles.forEach(dao::insertArticle)
    }

    override fun getAllArticles(): List<Article> = dao.getAllArticles()

    override fun deleteAllArticles() = dao.deleteAllArticles()
}

    • 第 19 行：对每个商品调用 [dao] 层的插入函数，而不向它传递事务；
    • 第 21 行：一次暂停模拟处理过程，以便让另一个线程有时间在事务期间介入（测试程序的第三部分）；

    • 第 32 行：在任何情况下，线程都不再有活动的事务：[remove()] 清除线程的值。如果线程会被重用（池化线程），这一点至关重要；

    8.12.5. 结论

    前面的例子展示了线程局部数据在事务管理中的价值。它不应被完全照搬，但它准确地描述了框架的工作方式：Spring 的事务管理（[@Transactional] 注解）把事务和数据库连接放入 [ThreadLocal] 中，数据访问层查询它们，而代码无需自己操作事务；Hibernate 同样可以把工作会话与当前线程关联起来。我们将在第 11 章再讨论这些工具。在新的代码中，特别是使用虚拟线程时，推荐使用 *[ScopedValue]* 来传递这类上下文信息；使用协程时，这一角色由协程上下文承担（第 9 章）。

    线程同步是一个具有挑战性的领域。本章介绍了主要的工具；如需深入了解：

    • Brian Goetz 等人的著作 [Java Concurrency in Practice] （Addison-Wesley），尽管它早于虚拟线程，但仍然是该主题的权威参考。它的示例是用 Java 写的，但它所讲的一切都适用于 JVM 上的 Kotlin；
    • Oracle Java 教程的“并发”部分：Lesson: Concurrency——它虽然陈旧，但对基础内容仍然准确；
    • [java.util.concurrent] 包的文档：Package java.util.concurrent，其中“Memory Consistency Properties”一节总结了“先于”（happens-before）关系；
    • Kotlin 标准库中 [kotlin.concurrent] 包的文档（[thread]、[withLock]、[read]、[write]、[getOrSet]…）：kotlin.concurrent；
    • 引入虚拟线程和作用域值的 Java 改进提案（JEP）：JEP 444: Virtual Threads 和 JEP 506: Scoped Values。

    在现代代码中，很少直接操作对象（[Thread]）。在 Java 中，我们更倾向于使用执行器（[ExecutorService]）、用于计算的并行流，以及用于涉及等待的任务的虚拟线程。Kotlin 拥有所有这些工具，但它还提供了自己的解决方案，将在下一章介绍：协程。协程是一种可以自行挂起（在网络访问、数据库访问或文件访问期间）而不阻塞执行它的线程的任务，之后可以恢复执行，并且可能在另一个线程中恢复；结构化并发确保没有协程被遗忘，并且错误和取消能正确传播。尽管如此，本章的概念仍然至关重要：协程在线程中运行，它们共享的数据必须使用相同的工具（锁、原子类、并发集合）来保护，或使用适用于协程的对应工具（[Mutex]、[Channel]…）。
